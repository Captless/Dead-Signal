# DEAD SIGNAL

## Implementation Plan and Production Specification

**Document status:** Final implementation specification\
**Project type:** Local-first, single-player, browser-based 3D game\
**Working title:** DEAD SIGNAL\
**Primary objective:** Build a complete, polished first-person zombie
survival shooter with original code-generated models, environments,
interface, effects, audio, progression, and local saves.\
**Implementation agent:** OpenCode\
**Target platform:** Windows desktop browser, developed and run locally\
**Primary resolution target:** 1920×1080, with responsive scaling for
smaller desktop windows\
**Art direction:** Stylized industrial horror with restrained cinematic
lighting\
**Network requirement at runtime:** None after dependencies are
installed and the production bundle is built

------------------------------------------------------------------------

# 1. Mission and Non-Negotiable Requirements

Build a playable indie-scale game, not a scene demo. The player must be
able to launch the game, understand its controls, fight enemies, earn
currency, buy upgrades, unlock parts of the map, die, restart, and
retain selected long-term records.

OpenCode must own implementation of the game code and all
project-authored assets. Do not require Blender, Unity, Unreal Engine, a
separate texture editor, a separate audio editor, paid services,
external asset packs, API keys, accounts, or a backend.

All runtime assets must be generated by code or authored as local
project files. Prefer procedural geometry, canvas-generated textures,
CSS, SVG, Web Audio, and small source-controlled configuration files. If
a visual requirement cannot be achieved to the required quality using
procedural techniques, implement the best coherent stylized alternative;
do not silently substitute generic primitives or claim photorealism.

## 1.1 Product goals

1.  A responsive, satisfying first-person combat loop.
2.  A coherent, distinctive visual identity across environment, enemies,
    weapons, effects, and UI.
3.  A small but thoughtfully composed map that supports tactical
    movement and enemy navigation.
4.  Four meaningfully different firearms, three enemy archetypes, wave
    progression, scrap currency, weapon upgrades, perks, and unlockable
    areas.
5.  A reliable local-only runtime with no server, login, telemetry,
    remote APIs, or online dependency.
6.  A maintainable codebase with explicit ownership boundaries,
    data-driven balance, deterministic game-state transitions, and
    testable systems.
7.  A complete game flow: boot, title screen, settings, tutorial,
    gameplay, pause, upgrade interactions, death, results, restart, and
    return to menu.
8.  Verified behavior, not just code generation. Every phase must be
    tested before expanding scope.

## 1.2 Non-goals for the initial release

Do not implement multiplayer, networking, user accounts, cloud saves,
mod support, a large open world, procedural map generation, crafting
trees, loot rarity systems, weapon attachment inventories, vehicles,
cinematic cutscenes, voice acting, a branching narrative, or a complex
boss fight.

Do not add a framework or dependency unless it solves a demonstrated
need. Do not overengineer an ECS, a plugin architecture, a custom
physics engine, or an elaborate event bus.

## 1.3 Definition of complete

The project is complete only when: - `npm run dev` launches a playable
local game. - `npm run build` succeeds without TypeScript errors. -
Automated tests pass. - The player can complete the intended gameplay
loop. - Every visible button and interaction has a working result. - No
critical console errors occur during a full play session. - Save/load,
pause/resume, death/restart, purchases, collision, enemy attacks, and
wave transitions have been verified. - The game remains usable when
graphics settings are reduced. - The README explains setup, controls,
architecture, and troubleshooting.

# 2. Product and Game Identity

## 2.1 Working title

**DEAD SIGNAL**

Subtitle used in menus: **QUARANTINE PROTOCOL**

The title implies an isolated industrial emergency and a mysterious
radio signal without requiring a story-heavy game. Do not add elaborate
lore systems. Environmental details and short UI messages are enough.

## 2.2 Premise

An industrial processing facility inside a sealed quarantine district
has gone dark. The player is an unnamed survivor who reaches the
facility while searching for a working communications relay. Infected
workers occupy the complex. The relay's signal repeats from deeper
inside, but the player must first survive, restore access, and acquire
better equipment.

Story is environmental context, not a blocker to gameplay. Convey it
through signage, warning lights, room composition, short radio text, and
a few optional inspectable details. Do not require dialogue trees or
voice acting.

## 2.3 Core game loop

1.  Start in the entry bay with a service pistol and a small amount of
    ammunition.
2.  Activate the facility's emergency power and begin the first wave.
3.  Fight infected enemies and earn scrap from kills and wave
    completion.
4.  Collect dropped ammunition only when a deliberately authored pickup
    is spawned; do not rely on random loot to sustain the game.
5.  Use safe windows between waves to reload, heal, buy upgrades, and
    choose the next objective.
6.  Spend scrap on weapons, weapon tiers, perks, and doors.
7.  Enter newly unlocked routes to reach stronger equipment and
    alternate combat spaces.
8.  Survive escalating waves, record the best wave, and choose to
    continue or restart after death.

Combat is the primary activity. Shopping and unlocking must be quick,
clear, and interruptible only in deliberate safe phases or while
interacting with a station.

## 2.4 Intended play session

A first successful run should be understandable within five minutes. The
game should support short sessions of approximately 10--25 minutes.
Long-term replayability comes from wave survival, purchase decisions,
difficulty settings, and improving the best-wave record, not from a
large amount of content.

# 3. Locked Technology Stack

Use a browser-based, TypeScript-first stack.

-   **Three.js:** 3D rendering, scene graph, camera, geometry,
    materials, lights, raycasting, and post-processing only if
    performance allows.
-   **TypeScript:** game logic and strict data contracts.
-   **Vite:** local development server and production bundling.
-   **HTML and CSS:** all menus, HUD, overlays, stations, settings, and
    accessibility controls.
-   **Web Audio API:** synthesized sound effects and procedural
    ambience.
-   **Vitest:** unit and integration tests for pure game logic and state
    transitions.
-   **Playwright only if already available or justified by the
    repository:** browser automation for critical smoke tests. Do not
    add it merely for appearance; if added, keep tests small and
    deterministic.
-   **IndexedDB or localStorage:** local settings and persistent
    records. Use localStorage for small, non-sensitive settings and
    best-wave data; use IndexedDB only if larger save structures
    genuinely need it.

Do not use React Three Fiber unless the repository already uses it and
retaining it clearly reduces risk. For a focused game with a custom game
loop and DOM UI, plain TypeScript plus Three.js is simpler and avoids a
second rendering abstraction.

## 3.1 Dependency rules

Use the current stable compatible versions available at implementation
time. Pin dependencies in the lockfile. Avoid unmaintained libraries and
unnecessary UI component frameworks.

Suggested initial dependencies: - `three` - `vite` - `typescript` -
`vitest` as a development dependency

Add a small navigation or collision helper only if a tested prototype
proves it is necessary. Prefer a simple custom grid-based navigation
system for this compact map over an unverified heavy dependency.

## 3.2 Local-only guarantees

At runtime: - No network requests. - No external fonts loaded from a
CDN. - No analytics, ads, telemetry, remote APIs, account system, or
backend. - No externally hosted models, textures, images, or audio. - No
runtime dependence on a remote repository. - No service worker unless
offline installation is explicitly implemented and tested; it is not
required for the initial release.

Use local system fonts or bundle any font files only when licensing and
local availability are verified. The base game must remain functional if
optional post-processing is disabled.

## 3.3 Repository-first rule

Before writing or changing code, inspect the current repository, package
files, scripts, existing documentation, tests, and `AGENTS.md`
instructions. Reuse existing valid infrastructure. Do not overwrite a
working project blindly, invent paths that do not exist, or create
duplicate systems. If the repository is empty, create the structure
specified in this document.

# 4. Visual Direction and Design System

## 4.1 Art direction

**Style:** handcrafted stylized industrial horror; readable silhouettes;
slightly exaggerated proportions; restrained material complexity;
dramatic but navigable lighting.

The game must look cohesive rather than photorealistic. Use a consistent
scale, a limited palette, purposeful roughness variation, beveled edges
where they catch light, and controlled surface wear. Avoid
default-looking primitives, random clutter, oversaturated neon,
excessive bloom, and uniform grunge applied to every object.

The visual target is a premium small indie game: strong composition and
art direction over raw polygon count.

### World palette

-   Concrete: cool gray-green, low saturation, moderate roughness.
-   Painted steel: charcoal, faded blue-gray, chipped edge accents.
-   Rust: burnt umber and muted orange-brown, concentrated at seams and
    water exposure.
-   Emergency lights: deep red, used sparingly for threat zones and
    alarms.
-   Powered equipment: muted teal/green indicators.
-   Warm practical lights: dusty amber, used for stations, lamps, and
    navigational focus.
-   Zombies: desaturated skin and clothing with selective readable
    injury accents. Avoid uniformly bright green bodies.
-   Weapon metal: dark graphite, worn steel edges, muted polymer,
    controlled warm reflections.

Keep the scene mostly neutral and dark, with localized warm and cool
light sources. The player must always be able to read enemy silhouettes
and walkable surfaces. Darkness is atmosphere, not a substitute for
level design.

## 4.3 Contrast and visual hierarchy

1.  Gameplay threats must read before decoration.
2.  Interactable objects use a restrained amber cue when the player is
    close enough.
3.  Critical HUD data must be readable at 1080p and scale down without
    clipping.
4.  UI backgrounds must maintain sufficient contrast over any scene.
5.  Avoid excessive transparency that causes world detail to compete
    with text.
6.  Use one primary display typeface style and one compact technical
    style at most. If no licensed bundled font is available, use system
    sans-serif and monospace fallbacks.
7.  Use consistent spacing units: 4, 8, 12, 16, 24, 32, 48 px.
8.  Use 1 px borders for most panels, 2 px only for active/critical
    states.
9.  Use short transitions, normally 120--220 ms. Never animate critical
    gameplay feedback so slowly that it obscures information.
10. No decorative emoji in the game UI.

## 4.4 Shape language

-   UI panels: squared or subtly clipped corners, not excessive rounded
    cards.
-   Buttons: clear label, distinct hover/focus/pressed/disabled states.
-   Icons: one consistent outline/glyph family authored as inline SVG or
    CSS; do not mix unrelated icon styles.
-   Environment: rectangular industrial forms, pipes, braces, panels,
    and repeated structural rhythm.
-   Weapons: recognizable silhouettes with layered components and a
    controlled amount of detail.
-   Zombies: asymmetry in posture, clothing, and limb proportions;
    silhouette is more important than tiny surface details.

## 4.5 Lighting and post-processing

Use a restrained lighting budget: - One primary directional or broad
ambient contribution as appropriate to the scene. - A small number of
shadow-casting lights near key gameplay areas. - Local point lights for
practical fixtures, with shadow casting disabled except for a few
critical lights. - Fog or atmospheric depth only if it improves
separation and does not conceal enemies. - Tone mapping and color-space
settings configured correctly for Three.js. - Optional subtle vignette
and restrained color grading if performance remains stable. - Bloom is
optional, low intensity, and must not wash out UI or enemy
silhouettes. - Avoid expensive real-time global illumination, excessive
transparent layers, and many shadow-casting point lights.

The map must remain navigable with low graphics settings and without
post-processing.

# 5. Game Flow and Screens

## 5.1 Boot flow

1.  Initialize renderer and core systems.
2.  Load local configuration and save data with safe fallbacks.
3.  Create or load the menu scene.
4.  Show the title screen.
5.  Start a new run only after the player selects Play and the required
    browser interaction has enabled audio and pointer lock.
6.  If WebGL initialization fails, show a readable error panel with
    troubleshooting instructions instead of a blank page.

## 5.2 Main menu

Design a cinematic but lightweight menu over a static or slowly animated
view of the entry bay. The environment should provide atmosphere without
spawning enemies or running full combat simulation.

Menu elements: - DEAD SIGNAL title and QUARANTINE PROTOCOL subtitle. -
`NEW RUN` primary action. - `CONTINUE` only if a resumable run is
intentionally supported; otherwise do not display it. - `SETTINGS`. -
`RECORDS`. - `CREDITS`. - Build/version label in a low-emphasis
position.

Do not include fake buttons, fake online status, or nonfunctional menu
entries. Credits should identify the project as locally
generated/authored, without claiming external assets or contributors
that were not used.

## 5.3 New-run setup

Keep the first-run flow short. Offer three difficulties: - **Recruit:**
slower escalation, more forgiving damage, more scrap. - **Standard:**
intended baseline balance. - **Containment:** faster escalation, more
incoming damage, less margin for mistakes.

Default to Standard. Explain each difficulty in one short sentence.
Difficulty affects explicit tuning multipliers and is saved per run.

## 5.4 Tutorial

Deliver tutorial prompts in the game world as compact, dismissible
instructions: - Move and look. - Aim and fire. - Reload. - Interact with
the power control. - Survive the first wave. - Buy one upgrade between
waves.

Tutorial prompts must disappear after the action is completed or after
the player dismisses them. Do not repeatedly interrupt combat. Provide a
Controls section in Settings.

## 5.5 Pause menu

Pause must stop: - Player movement and firing. - Enemy AI and
movement. - Wave timers and spawn scheduling. - Damage and attack
wind-ups. - Weapon reload timers. - Gameplay particles where practical.

The pause menu must offer Resume, Settings, Restart Run, and Return to
Main Menu. Confirm destructive actions. Do not allow the game to
continue simulating behind a modal.

## 5.6 Death and results

When health reaches zero: - Disable player combat and movement. - Stop
new spawns and enemy attacks. - Allow only a short, controlled death
presentation. - Display wave reached, kills, scrap earned, enemies
defeated, and elapsed time. - Update best-wave and other local records
safely. - Offer Retry and Main Menu.

Do not make death screens depend on long unskippable animations.

  `F`                                 Toggle flashlight if flashlight is

Do not implement a key just because it is listed here. Remove optional
controls from the final help panel if the associated mechanic is not
shipped. The minimum required controls are movement, look, fire, reload,
interact, weapon switching, and pause.

## 6.2 First-person controller

-   Use pointer lock after explicit player input.
-   Show a clear overlay when pointer lock is not active.
-   Clamp vertical look to avoid camera inversion.
-   Apply delta-time-based movement so behavior does not depend on frame
    rate.
-   Separate horizontal movement from camera rotation.
-   Implement acceleration/deceleration only if it improves feel; do not
    make controls sluggish.
-   Add modest head bob only if it is comfortable and can be disabled.
-   Weapon sway and recoil must be small, readable, and not cause
    nausea.
-   Keep the weapon inside the camera view and prevent clipping through
    walls where practical.
-   Use collision checks for player movement; never allow the player to
    walk through map walls or doors.
-   Prevent jumping from becoming an unintended way to bypass map
    boundaries.
-   Reset input state correctly on blur, pointer-lock loss, pause, and
    death.

## 6.3 Accessibility and comfort

Settings: - Mouse sensitivity. - Invert vertical look. - Master,
music/ambience, and effects volume. - Camera shake on/off. - Head bob
on/off. - Reduced flashes option. - Graphics preset. - FOV within a safe
practical range, default approximately 80 degrees vertical or equivalent
configured camera FOV. - Reticle visibility and scale. - Optional
color-independent status icons.

Avoid strobing lights and repeated full-screen white flashes. Damage
flashes must be brief, subtle, and disabled or reduced by the
reduced-flashes setting.

# 7. Combat Specification

## 7.1 Combat principles

-   Enemies must telegraph attacks.
-   Player feedback must distinguish hit, kill, blocked shot, empty
    magazine, and reload.
-   Weapon recoil must be controllable, not random enough to make aiming
    feel arbitrary.
-   Ammo is finite, but the player must have a reliable way to obtain
    ammunition through purchases or authored pickups.
-   Headshots reward accuracy but should not make body shots useless.
-   Enemies must not damage the player through walls.
-   Attack cooldowns and hit reactions must prevent unfair damage
    stacking.
-   Enemy counts and effects must be bounded for performance.

## 7.2 Shooting model

Use raycasting/hitscan for firearms in the initial release. This is
simpler and responsive. Projectiles are not required for ordinary
bullets.

On fire: 1. Verify game state, weapon ownership, magazine ammo, fire
cooldown, and player status. 2. Determine shot direction from the
camera/reticle. 3. Apply configured spread and recoil. 4. Raycast
against eligible damageable entities and environment collision. 5. Apply
damage to the first valid hit, including a hit-zone multiplier. 6. Spawn
a suitable impact effect at the hit point. 7. Play the weapon sound and
muzzle effect. 8. Update ammo and HUD. 9. Emit a testable combat event
or call the owning system directly; avoid a global event bus unless
there is a demonstrated need.

Do not use visuals as collision. Invisible hitboxes must match the
actual target reasonably closely.

## 7.3 Damage and hit zones

Minimum hit zones: - Head: configured multiplier, default 2.0×. - Body:
1.0×. - Limbs: 0.75× if reliable hit-zone detection is implemented;
otherwise use body damage rather than a fake feature.

Critical hit feedback: - A distinct but restrained reticle hit marker. -
Different confirmation for a headshot. - Kill confirmation only on
death. - Optional floating damage values disabled by default to preserve
visual clarity.

## 7.4 Player health and damage

Recommended starting values for tuning: - Player health: 100. - Starting
armor: 0. - Standard zombie contact/melee damage: approximately 12--18
depending on difficulty. - Short post-hit damage cooldown: enough to
prevent a single overlap frame from applying repeated damage, but not so
long that multiple enemies become harmless.

Use a clear invulnerability/cooldown rule after a successful enemy hit.
Prefer per-attacker cooldown plus a short player damage grace interval,
tuned to avoid both instant death from overlap and exploitative
invulnerability.

Health cannot exceed its maximum. Healing cannot revive a dead player.
Armor absorbs a defined fraction of incoming damage and depletes
accordingly; document whether damage overflow carries into health and
test it.

-   Weapon slot switching only selects owned weapons.

-   Double-clicks or repeated input must not charge twice.

Patrol rifle: 950 scrap. - Door costs: 300--700 scrap depending on the
route and value. - These values must be balanced against kill rewards
and wave rewards so the player can make at least one meaningful purchase
early without making all later purchases trivial.

# 9. Weapon Upgrades, Perks, and Economy

## 9.1 Currency

Primary currency: **SCRAP**.

Use the amber UI accent. Display the exact amount in the HUD and
purchase panels. Do not introduce multiple currencies.

Starting reward targets: - Standard infected kill: 20 scrap. - Rusher
kill: 25 scrap. - Brute kill: 45 scrap. - Wave completion: a fixed
reward that rises gradually with wave number. - Optional
first-headshot/precision bonus: small, capped, and not farmable through
repeated hits on the same target.

Rewards are granted once per death and once per completed wave. Ensure
enemy death events cannot be processed more than once.

## 9.2 Weapon upgrade tiers

Each weapon has three upgrade tiers after its base state. Use a single
upgrade station, with clear cost and effect preview.

-   **Tier I:** approximately 350 scrap; modest damage or handling
    improvement.
-   **Tier II:** approximately 650 scrap; a second meaningful stat
    improvement.
-   **Tier III:** approximately 1,000 scrap; strong but controlled
    specialization and a visual upgrade detail.

Each weapon's upgrade definition must specify: - Cost. - Prerequisite
tier. - Exact stat modifiers. - Visual change, if any. - Purchase
feedback. - Whether the upgrade persists only for the current run.

Upgrades apply to the owned weapon instance. They must not alter base
definitions shared by other weapons or affect a weapon the player has
not purchased.

Do not make every tier a universal damage multiplier. Differentiate
weapon paths through accuracy, reload, magazine size, spread, recoil, or
damage as appropriate.

## 9.3 Perks

Ship three simple perks: 1. **Field Dressing:** increase maximum health
or improve healing effectiveness, not both unless balance requires it.
2. **Steady Hands:** reduce recoil/spread modestly. 3. **Scavenger:**
earn a modest additional scrap percentage.

Each perk has a clear one-time purchase cost and effect. No hidden
stacking exploits. The UI shows owned status and exact benefit. Perks
persist for the current run only, unless a future design explicitly
changes this.

## 9.4 Healing and ammunition

-   One healing item restores a configured amount, default 35 health,
    without exceeding maximum health.
-   Healing has a short use animation/timer and is interrupted by death;
    interruption behavior must be consistent.
-   Ammunition refill purchases are available at the armory or upgrade
    station.
-   Reserve ammo is capped.
-   Purchases are disabled if the player is dead, paused, out of station
    range, or lacks currency.
-   Every disabled purchase explains why.

## 9.5 Transaction integrity

Purchases must be atomic from the game's perspective: 1. Validate state,
price, prerequisites, range, and inventory capacity. 2. Deduct currency.
3. Apply the purchase. 4. Emit confirmation and update the UI. 5. If
applying the purchase fails, roll back the deduction or ensure the
purchase is designed so application cannot fail after validation.

Never allow negative scrap, duplicate ownership, repeated rewards, or
purchases after death.

# 10. Enemy Design and AI

## 10.1 Enemy archetypes

### Drifter --- standard infected

-   Medium speed, medium health, close-range melee attack.
-   Clear forward-facing posture and readable attack wind-up.
-   Baseline enemy used in early waves.
-   Low-cost to render and animate.

### Rusher --- fast infected

-   Lower health, higher movement speed, shorter approach time.
-   Distinct lean-forward run animation and silhouette.
-   Introduced after the player has learned standard combat.
-   Must not spawn directly behind the player without a readable route
    or warning.

### Brute --- heavy infected

-   High health, slow movement, powerful attack, clear recovery window.
-   Broad silhouette and visibly heavier animation.
-   Appears in later waves and is not spammed.
-   Damage and health must not turn it into a tedious bullet sponge.

## 10.2 AI state machine

Each enemy uses a finite state machine: - `spawn` - `idle/alert` -
`pursue` - `attackWindup` - `attack` - `recover` - `hitReact` -
`staggered` if applicable - `dead`

Transitions must be explicit. Prevent invalid state combinations such as
attacking while dead or pursuing while paused.

## 10.3 Navigation

The map is compact and authored. Use a simple grid or waypoint graph: -
Define walkable navigation cells/nodes. - Mark walls, closed doors,
hazards, and blocked props. - Recompute routes only when needed, not
every frame for every enemy. - Use local steering/separation to reduce
enemy stacking. - Keep enemy movement stable and bounded. - Use a simple
fallback if a path is temporarily unavailable. - Do not allow enemies to
move through closed doors or solid geometry. - If an enemy is stuck for
a configured interval, recalculate a route or move to a valid nearby
node; do not teleport in front of the player.

For the first playable prototype, direct pursuit in a test arena is
acceptable. Full navigation must be completed before the final map is
considered playable.

## 10.4 Enemy attacks

-   Telegraph attack with animation and/or audio.
-   Check range, facing, and line of sight at the actual damage frame.
-   Apply damage once per attack.
-   Use cooldowns and recovery windows.
-   Cancel or safely resolve an attack if the player dies or the game
    pauses.
-   No damage through walls.
-   Use collision/spacing to avoid every enemy occupying the same exact
    point.
-   Attack cadence must give the player a fair opportunity to respond.

## 10.5 Enemy animation

Generate simple but purposeful animation clips using procedural rig
transforms: - Idle breathing/weight shift. - Walk. - Run for Rusher. -
Attack wind-up and strike. - Hit reaction. - Death/fall. -
Brute-specific heavy wind-up and recovery.

Use a consistent skeleton hierarchy and shared animation utilities where
practical. Do not attempt complex facial animation. If a full skinned
rig is too expensive to implement robustly, use a simple hierarchical
rig with clearly articulated limbs and tested animation. Avoid stiff
unanimated capsules as final enemies.

# 11. Wave Director and Difficulty

## 11.1 Wave rules

-   Wave 1 begins with a small, readable group.
-   Each completed wave grants its reward once.
-   A short between-wave interval allows reloading, buying, and
    repositioning.
-   The next wave begins automatically after a visible countdown, with
    an option to start early if it does not create race conditions.
-   A wave is complete only when all scheduled enemies have spawned and
    all living enemies are dead.
-   No wave can be completed merely because the spawn queue is empty.
-   If an enemy is stuck or fails to spawn, the game must not deadlock
    indefinitely. Log the failure in development and recover safely.

## 11.2 Wave composition

Use a data-driven wave director. Suggested pattern: - Waves 1--2: mostly
Drifters. - Waves 3--4: introduce limited Rushers. - Waves 5--6:
introduce one Brute with supporting enemies. - Later waves: scale enemy
count and mix archetypes gradually. - Never exceed the active-enemy
budget. - When the budget is full, delay spawns rather than creating an
uncontrolled performance spike.

Avoid purely exponential scaling. Use a controlled progression curve
with a cap on simultaneous enemies and diminishing growth after the
early waves.

## 11.3 Difficulty modifiers

Recruit: - Lower enemy damage and slower escalation. - More generous
scrap rewards. - More forgiving early wave composition.

Standard: - Baseline health, damage, spawn pacing, and economy.

Containment: - Higher enemy pressure and damage. - Lower reward
generosity or higher upgrade pressure, but not both to an unfair
degree. - Earlier introduction of mixed enemy types.

All multipliers must be explicit in a single difficulty configuration.
Do not duplicate difficulty conditionals across unrelated systems.

## 11.4 Spawn fairness

-   Spawn enemies at authored spawn points outside the player's
    immediate view when possible.
-   Maintain minimum distance from the player.
-   Avoid spawning inside walls, props, the player, or newly closed
    doors.
-   If no fair spawn point exists, wait rather than force a bad spawn.
-   Use a subtle cue or audio signal for a new wave.
-   Never place a Brute directly next to the player without a designed
    encounter.

# 12. Map and Level Design

## 12.1 Map name

**Processing Block 07**

One handcrafted compact facility, not a procedural maze.

## 12.2 Zones

1.  **Entry Bay:** starting area, tutorial space, safe initial
    sightlines.
2.  **Processing Hall:** main combat arena with readable lanes, pillars,
    machinery, and multiple approaches.
3.  **Maintenance Loop:** narrower route that supports flanking and
    controlled choke points.
4.  **Armory:** weapon purchases and ammunition.
5.  **Power Room:** upgrade station and facility power control.
6.  **Upper Catwalk:** limited verticality and an alternate sightline,
    not a safe exploit where enemies can never reach the player.
7.  **Relay Chamber:** late unlock and environmental story endpoint. No
    full boss required in the initial release.

## 12.3 Layout principles

-   Build loops rather than dead-end corridors wherever possible.
-   Every combat area needs at least two readable escape or
    repositioning options.
-   Avoid visual clutter that blocks aim or obscures enemies.
-   Cover must have consistent collision and must not trap the player.
-   Use lighting and architectural landmarks to distinguish rooms.
-   Door openings must be wide enough for player and enemy collision.
-   Enemy pathing must be tested from every spawn point to every combat
    zone.
-   Place purchase stations where players can safely understand and use
    them.
-   Do not use invisible walls where a visible architectural boundary
    can communicate the limit.
-   Mark locked doors with consistent visual and UI language.

## 12.4 Procedural environment kit

Create reusable, parameterized builders for: - Floor sections and
trim. - Wall sections and corners. - Door frames and doors. - Pillars
and beams. - Pipes and elbows. - Cable trays. - Industrial lamps. -
Control panels. - Storage crates and barrels. - Workbenches. - Railings
and catwalk pieces. - Warning signs and decals. - Vents and grates. -
Machinery silhouettes. - Breakable or destructible props only if the
core game is already stable.

All dimensions must follow one world-scale convention. Suggested player
height is around 1.75--1.85 world units. Doors, railings, cover,
weapons, and enemy models must be proportioned against the same scale.

Do not scatter random props. Each prop must serve navigation, cover,
environmental storytelling, lighting composition, or visual rhythm.

# 13. Procedural Asset Production Rules

## 13.1 General quality standard

Every important asset needs: - A recognizable silhouette. - Coherent
proportions and scale. - More than one visual feature where
appropriate. - Material differentiation. - Intentional bevels or edge
breaks where they catch light. - Surface variation that supports the
material rather than obscures it. - A clear reason for its placement. -
A performance budget. - A validation screenshot or visual review during
development.

A model made from primitive geometry is not automatically bad. It
becomes generic when primitives are left unmodified, uniformly colored,
unscaled, and arranged without a design language. Combine custom
geometry, layered parts, material variation, bevel-like geometry, and
purposeful composition.

## 13.2 Weapons

Build each weapon from separate, named mesh components: - Main
receiver/body. - Barrel and muzzle. - Grip. - Magazine. - Sights. -
Trigger/guard silhouette. - Stock or pump assembly where relevant. -
Small restrained details such as screws, rails, and panels. - Optional
upgrade-specific parts.

Use a small number of materials per weapon. Avoid hundreds of separate
draw calls for tiny details. Group or instance repeated details when
practical. Make reloads visible and synchronize ammo changes with the
correct animation event.

## 13.3 Zombies

Use a common base rig and separate archetype configurations. Vary: -
Body proportions. - Clothing shape. - Posture. - Color/material
accents. - Movement speed and animation. - Damage response.

Use layered clothing geometry and deliberate asymmetry. Keep hitboxes
stable and independent from decorative mesh detail. Use a small set of
reusable materials, not a unique expensive material for every body part.

## 13.4 Textures

Generate canvas textures locally: - Concrete mottling. - Steel roughness
and scratches. - Rust patches. - Painted stripes. - Labels and warning
symbols. - Weapon wear. - Clothing fabric variation. - Blood/injury
accents in restrained amounts.

Use correct color-space settings for color maps. Data textures such as
roughness/normal-like maps must not be treated as color textures. Keep
resolution modest and reuse textures. Prefer procedural variation and
shader/material parameters over huge texture files.

## 13.5 VFX

Required: - Muzzle flash per weapon. - Bullet impact sparks for metal. -
Dust/concrete impact for walls. - Hit response on enemies. - Brief blood
impact effect if enabled by settings. - Death particles only when
inexpensive and visually restrained. - Purchase confirmation. -
Wave-start cue. - Damage feedback. - Door/power activation effects.

Use object pools for frequently spawned particles. Effects must have
lifetimes and hard caps. Never create unlimited particles or allocate a
new material every frame.

## 13.6 Audio

Use Web Audio synthesis for: - Pistol, shotgun, SMG, and rifle firing
profiles. - Reload/empty click/weapon switch. - Footsteps. - Enemy
alert, movement, attack, hit, and death. - Door and power switch. -
Upgrade purchase. - Wave start and completion. - Player damage and
death. - UI hover/confirm/back. - Ambient industrial hum, ventilation,
distant metallic creaks, and restrained alarms.

Synthesis should use layered noise, filtered noise, oscillators,
envelopes, and short reverberation where appropriate. Do not make every
sound a generic beep. Each sound must have an envelope, frequency
profile, and volume suited to its role. Avoid excessive loudness and
clipping. Provide independent master, ambience, and effects volume
controls.

Audio starts only after user interaction to comply with browser autoplay
restrictions. Pause and resume must handle audio state correctly.

Station sections: - Weapons. - Weapon upgrades. - Perks. - Ammunition. -

change. - Prerequisites. - Owned/maxed/locked/insufficient-scrap

## 14.4 Settings

-   Master volume.
-   Ambience volume.
-   Effects volume.
-   Mouse sensitivity.
-   Invert vertical look.
-   FOV.
-   Camera shake.
-   Head bob.
-   Reduced flashes.
-   Graphics preset: Low, Medium, High.
-   Reticle size.
-   Reset to defaults.

Changes apply immediately when safe and persist locally. Include a reset
confirmation. Graphics options must correspond to real settings, not
decorative dropdowns.

## 14.5 UI motion

-   Hover: subtle brightness/edge change.
-   Press: immediate depressed state.
-   Purchase success: brief amber/teal confirmation and sound.
-   Insufficient currency: concise message, no shaking modal.
-   Wave transition: short, high-contrast title with minimal movement.
-   Death: brief controlled transition; keep text readable.
-   Reduced-motion/flash settings must reduce relevant effects.

Do not use endless animated gradients, excessive glassmorphism, giant
rounded cards, or generic SaaS-style layouts. This is a game interface,
not a dashboard.

# 15. Game State and Architecture

## 15.1 Architecture principles

-   One authoritative game state.
-   One game loop with delta-time handling and clamped large deltas
    after tab suspension.
-   Explicit ownership of player, weapons, enemies, waves, world
    interactions, audio, UI, saves, and settings.
-   Pure functions for balance calculations, reward calculations,
    purchase validation, and state transitions where practical.
-   Data-driven definitions for weapons, enemies, perks, upgrades,
    waves, and difficulty.
-   No direct DOM manipulation scattered across gameplay systems.
-   No gameplay state hidden in CSS classes.
-   No global mutable state except a small, explicit application root if
    necessary.
-   No unbounded per-frame allocations.
-   Dispose geometries, materials, listeners, timers, and audio nodes
    when their owning systems are destroyed.

## 15.3 State machine

Minimum top-level states: - `BOOT` - `MAIN_MENU` - `RUN_SETUP` -
`TUTORIAL` - `PLAYING` - `INTERMISSION` - `STATION` - `PAUSED` -
`PLAYER_DEAD` - `RESULTS` - `ERROR`

Define allowed transitions centrally. Examples: -
`MAIN_MENU → RUN_SETUP → TUTORIAL → PLAYING` -
`PLAYING → INTERMISSION → PLAYING` -
`INTERMISSION → STATION → INTERMISSION` - `PLAYING → PAUSED → PLAYING` -
`PLAYING → PLAYER_DEAD → RESULTS` - `RESULTS → RUN_SETUP` - Any safe
menu state may return to `MAIN_MENU`.

Do not allow `PLAYER_DEAD → PLAYING` without starting a new run. Pausing
from a state where pause is not meaningful must be blocked. UI and
simulation must use the same authoritative state.

## 15.4 Update order

Use a documented deterministic update sequence: 1. Read input. 2.
Resolve state-level controls. 3. Update player movement and collision.
4. Update weapon timers and firing. 5. Update enemy AI/navigation. 6.
Resolve combat and damage. 7. Update wave director and spawn scheduling.
8. Update interactables and pickups. 9. Update effects and animation.
10. Update audio parameters. 11. Render 3D scene. 12. Refresh only the
necessary UI values.

Avoid updating the full DOM tree every frame. Update HUD elements when
values change or at a bounded refresh cadence.

## 15.5 Error handling

-   Catch initialization errors and show a visible error screen.
-   Treat save data as untrusted and validate it before use.
-   Use safe defaults if a saved field is missing or invalid.
-   Log detailed development errors to the console, but do not expose
    stack traces in the normal UI.
-   Do not silently swallow exceptions.
-   Ensure a failed optional effect does not crash gameplay.
-   Clean up event listeners and renderer resources on restart or app
    teardown.
-   Guard against multiple animation loops being started.

# 16. Persistence and Save Rules

Persist: - Audio settings. - Mouse sensitivity and control
preferences. - Graphics settings. - Best wave reached. - Total kills and
best survival time if implemented. - Selected difficulty preference.

For the initial release, do not persist every live enemy, active wave
timer, and exact world position. Resume-in-progress saves introduce
avoidable consistency issues. Starting a new run should reset run-scoped
currency, ammo, perks, unlocked doors, kills, and current wave.

Save format must include a schema version. Validate values, clamp
numeric ranges, and recover from malformed JSON or failed storage
access. If storage is unavailable, the game must still be playable for
the current session and show a non-blocking notice if persistence cannot
be saved.

Provide a `Reset Records` action with confirmation. Do not clear
settings when clearing gameplay records unless the user explicitly
chooses a full reset.

# 17. Performance Budget

Treat performance as a design constraint, not a final optimization task.

## 17.1 Targets

-   Target 60 FPS at 1080p on the target laptop with the Medium preset.
-   Low preset must materially reduce GPU cost.
-   Aim for stable frame pacing; do not judge performance only by
    average FPS.
-   Start with a configurable active enemy cap, approximately 12--16,
    and raise only after profiling.
-   Use a hard cap for active particles and short-lived effects.
-   Keep texture dimensions modest and avoid unnecessary high-resolution
    render targets.
-   Use instancing for repeated static props where it is beneficial.
-   Reuse geometries and materials.
-   Limit shadow-casting lights.
-   Avoid per-frame geometry/material creation.
-   Avoid frequent garbage collection spikes from large temporary arrays
    and objects.

## 17.2 Graphics presets

**Low** - Disable post-processing. - Low shadow map resolution or
shadows disabled for secondary lights. - Reduced particles. - Lower
render scale if needed. - Reduced ambient effects.

**Medium** - Main shadows enabled at moderate resolution. - Limited
particles. - Restrained post-processing if profiling supports it. -
Default preset.

**High** - Higher shadow resolution. - More particle detail. - Optional
post-processing. - No feature may be required for gameplay or
readability.

## 17.3 Profiling checkpoints

Measure after: 1. Empty scene and player controller. 2. Complete map. 3.
Maximum intended enemy count. 4. Full weapon fire and impact effects. 5.
Worst-case wave with all systems active.

If performance falls below target, reduce expensive lighting, shadow
count, particles, overdraw, and geometry before reducing essential
gameplay fidelity. Record actual measurements instead of claiming
performance without testing.

# 18. Testing and Quality Assurance

## 18.1 Automated tests

Write tests for pure logic and critical state transitions: - Weapon fire
cooldown and ammunition consumption. - Reload transfer, reserve caps,
and interrupted reload rules. - Damage calculation and headshot
multiplier. - Player death and prevention of post-death damage. - Enemy
reward awarded exactly once. - Wave completion only after all scheduled
and living enemies are resolved. - Wave rewards granted exactly once. -
Scrap cannot become negative. - Purchase validation and transaction
behavior. - Upgrade prerequisites and stat calculations. - Difficulty
modifiers. - Save schema validation and migration/default fallback. -
Settings clamping. - State transition validity. - Enemy cap and spawn
scheduling behavior.

Tests must not depend on random values unless the random generator is
seeded or mocked.

## 18.2 Manual gameplay test checklist

### Startup

-   Fresh install starts without saved data.
-   Corrupted save does not crash the game.
-   WebGL failure produces a readable message.
-   Menu buttons work and have visible focus states.

### Player

-   Mouse look and movement work.
-   Player cannot pass through walls, doors, or solid props.
-   Player cannot escape map boundaries.
-   Input does not stick after alt-tab, pause, or pointer-lock loss.
-   Pause and resume do not create extra game loops.

### Weapons

-   Each weapon fires at its configured rate.
-   Ammo decreases correctly.
-   Reload uses only reserve ammo.
-   Empty weapons cannot fire.
-   Switching weapons preserves ammo and upgrade state.
-   Shots stop at walls.
-   Headshots and body hits produce correct damage.
-   Effects and sound correspond to the weapon used.

### Enemies

-   Each archetype has distinct movement and stats.
-   Enemies navigate around intended obstacles.
-   Enemies do not attack through walls.
-   Attack damage occurs once per attack.
-   Dead enemies cannot attack or award repeated rewards.
-   Stuck enemies recover or fail safely.

### Progression

-   Scrap rewards are granted once.
-   Purchases validate price and prerequisites.
-   Insufficient scrap disables or rejects purchase correctly.
-   Repeated input cannot double-purchase.
-   Weapon upgrades change actual weapon stats.
-   Doors unlock once and remain passable.
-   Healing and ammo refills obey limits.

### Waves

-   Wave begins and ends correctly.
-   Between-wave interval works.
-   Wave reward is granted once.
-   Enemy cap is respected.
-   Difficulty changes actual gameplay.
-   Restart resets run-scoped state.

### UI and settings

-   HUD values match actual game state.
-   UI remains legible against all lighting conditions.
-   All buttons perform their advertised action.
-   Audio sliders work and persist.
-   Graphics settings change actual rendering behavior.
-   Reduced-flash and camera comfort settings work.
-   No modal traps the player without a working exit.

### Stability

-   Play at least 10 consecutive waves or a defined long-session test.
-   Restart several times.
-   Return to menu and start a new run.
-   Inspect browser console for errors.
-   Check renderer and audio resources for leaks after repeated
    restarts.
-   Confirm the game still works with graphics set to Low.

# 20. OpenCode Execution Instructions

OpenCode must implement the project in small, verifiable phases. It must
not attempt to generate the entire game in one enormous change.

## 20.1 Before every phase

1.  Read `AGENTS.md`, this plan, README, and relevant existing source
    files.
2.  Inspect the actual project structure and current git status.
3.  Identify what is already implemented and reuse it.
4.  State the smallest set of files and systems needed for the current
    phase.
5.  Implement only that phase and its required dependencies.
6.  Run the relevant checks and inspect errors.
7.  Fix regressions before marking the phase complete.
8.  Update a concise progress section in the implementation plan or a
    separate progress document only if it adds durable value. Do not
    create redundant tracking documents.

## 20.2 Code quality rules

-   Use strict TypeScript; avoid `any` unless justified and isolated.
-   Do not use type assertions to conceal invalid assumptions.
-   Do not put the entire game in one file.
-   Do not create generic abstractions before two real use cases require
    them.
-   Do not duplicate balance constants.
-   Avoid magic numbers in gameplay systems; use named configuration
    values.
-   Use stable ownership and disposal for Three.js resources.
-   Use delta time and handle tab suspension.
-   Use seeded or injectable randomness for testable systems.
-   Keep pure game logic independent of Three.js where possible.
-   Separate game state from DOM presentation.
-   Use meaningful names and explicit interfaces.
-   Avoid unnecessary comments that merely restate code; document
    non-obvious rules and invariants.
-   Do not disable lint/type/test checks to force a green result.
-   Do not remove tests because they fail; fix the implementation or
    correct a demonstrably wrong test.
-   Do not claim visual quality without inspecting the running result.
-   Do not claim browser testing occurred unless the game was actually
    opened and exercised.
-   Do not fabricate screenshots, test outcomes, or performance
    measurements.

## 20.3 Asset quality rules

-   No unmodified default cubes, spheres, or capsules as final hero
    assets.
-   Primitive geometry is allowed as a construction technique when
    shaped, layered, proportioned, and materialized intentionally.
-   Avoid random prop scatter without level-design intent.
-   Every weapon must be visually distinct.
-   Every enemy type must have a different silhouette and movement
    profile.
-   Maintain the defined palette and material language.
-   Keep visual effects readable and bounded.
-   Prefer authored procedural detail over excessive geometry.
-   Validate weapon alignment from the actual player camera.
-   Validate character animation from gameplay distance, not just
    close-up.

## 20.4 Token and scope discipline

-   Inspect first; do not repeatedly rescan unchanged files.
-   Use focused implementation tasks with explicit acceptance criteria.
-   Avoid repeatedly rewriting the full plan into prompts.
-   Do not add features outside scope without identifying the cost and
    benefit first.
-   If a phase reveals an architectural problem, fix the smallest
    underlying cause rather than layering a workaround.
-   Prefer one complete, tested feature over many half-implemented
    systems.
-   Keep progress reports short: completed, tested, known issues, next
    phase.
-   Stop and report a real blocker instead of fabricating a solution.

## 20.5 Git discipline

-   Inspect branch and working tree before editing.
-   Never discard user changes.
-   Avoid destructive commands such as hard reset or forced checkout
    unless the user explicitly authorizes them.
-   Make coherent commits only when requested or when the repository
    workflow calls for them.
-   Do not merge, push, publish, or deploy without explicit
    authorization.
-   Keep generated build artifacts and local caches out of version
    control.
